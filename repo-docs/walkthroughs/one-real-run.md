# 一个文件读取请求怎样获得一次执行

客户端想读取工程中的文件时，云端认证先确认客户端身份和权限。读取本身仍须本机查看精确参数并批准，避免把云端中继的身份判断直接变成宿主操作权。以下使用测试中的中性路径说明过程。

难点是一个合法客户端也可能提出不可信操作，必须让本机批准绑定精确参数，并在副作用前消费和登记。

## Step 1: 身份与请求到达本地边界

云端中继把已认证的工具请求、客户端身份、权限和截止时间装入请求信封。连接器再次检查客户端、工具权限、JSON-RPC 结构和时限；未知工具或过期请求在触碰文件前被拒绝。[本地请求策略](../../local/request-policy.mjs)中的 `validateRequestEnvelope` 定义本地边界，[云端中继](../../cloud/relay.mjs)负责请求与对应连接、响应和取消信号的交接。

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "read_file",
    "arguments": { "path": "/workspace/canary.txt" }
  }
}
```

这是中性示例。真实访问范围由安装配置决定，工程目录可能含密钥；批准前必须核对实际文件与用途。

## Step 2: 未批准请求先进入本机队列

敏感文件和命令工具首次调用返回 `LOCAL_APPROVAL_REQUIRED`，实际操作尚未执行。待处理记录绑定网关来源、客户端及权限、方法和全部参数；其摘要在本机保存。查看环境、查询任务和停止自有任务属于明确豁免，但仍需身份和权限检查。

批准从默认受保护目录 `%USERPROFILE%\.agentdock-bridge` 的 `Approve.cmd` 进入，查看完整参数后输入显示的批准文本。批准 5 分钟有效，只使用一次。网关来源、客户端、权限、方法和全部参数必须匹配；参数改变要重新批准。客户端 JSON-RPC `id` 用于关联响应，不属于批准对象，因此同参数重试可以使用新的 RPC ID。[批准状态机](../../local/approvals.mjs)与[记录校验](../../local/approval-store.mjs)共同保证摘要和时效匹配。

待处理记录使用紧凑 JSON，并在创建临时文件前检查最终 UTF-8 字节数；写入和读取都受 1,200,000 字节上限约束。例如，嵌套元数据不会因缩进膨胀而生成界面读不出的记录；若完整记录仍超限，请求明确失败，不进入待批准队列。元数据和所有参数仍完整参与批准摘要，不能通过删字段让超限请求获得另一种含义的批准。

## Step 3: 同参数重试消费批准并登记执行

相同参数重试会先消费本机批准，再为云端生成的桥接请求 ID 写入执行账本，最后进入运行器。桥接请求 ID 与上一步的客户端 RPC ID 用途不同：它用于阻止同一个桥接请求再次执行。已经尝试过的桥接 ID 不会再次执行，也不会重放文件正文或命令输出。这个设计限制重复副作用，但不能把断线或超时解释为“什么都没做”。[连接器交接](../../local/connector.mjs)按此顺序调用批准、账本和运行器。

| 请求情形 | 可观察结果 |
| --- | --- |
| 首次请求，未批准 | `LOCAL_APPROVAL_REQUIRED`，不执行 |
| 同一客户端、同参数、有有效批准 | 消费批准后执行一次 |
| 路径或联网参数变化 | 重新要求批准 |
| 最终批准记录超过字节上限 | 明确拒绝，缩小请求后重新提交 |
| 再次使用已尝试桥接 ID | `already_attempted` 或 ID 冲突，不重放操作 |

这些分支由[连接器回归](../../test/connector.test.mjs)和[批准记录回归](../../test/approval-budget.test.mjs)验证；实际运行结果见[修复验收记录](../../SECURITY-FIXES.md)。

## Step 4: 容器执行并返回受限结果

敏感操作通过 Docker broker，文件工具还要检查路径、链接、文本编码和文件身份。命令使用 Linux Bash，默认无网络；显式 `network: "outbound"` 是批准内容的一部分。工程挂载可读写，容器隔离不等于工程内容可信，工具输出仍是待分析数据。

[沙箱接线](../../local/sandbox.mjs)连接[容器命令运行器](../../container/runner.mjs)和[文件运行器](../../container/file-worker.mjs)。它不向 Windows 宿主开放任意直接执行。连接器重启不会恢复旧后台任务；断线、取消或容器清理不确定时需核对实际状态，不能盲目重试写入。

例如，一个任务的容器清理失败时，连接器停止接纳新的命令和文件操作，但客户端仍可查询、停止自己尚在运行的其他任务。这些控制请求继续检查任务归属和取消状态，不因故障放宽权限；未确认清理的任务保留 `cleanup_confirmed: false`，需在本机检查 Docker，不能把控制请求返回当作清理成功。失败清理不自动重试，容器自身时限和可信本机停止入口继续有效。

## Step 5: 用回归验证批准与故障边界

在安装依赖后的独立开发环境可运行：

```sh
node --test test/connector.test.mjs test/approval-budget.test.mjs test/sandbox-recovery.test.mjs
npm run check
```

连接器测试使用临时状态目录、本机测试 WebSocket 和假的运行器，检查单次批准、变更参数和跨重启去重；批准预算测试检查完整记录的字节上限。故障恢复测试直接导入沙箱源码，仅模拟 Docker 进程边界，检查清理失败后自有任务可查询、可停止，新操作仍被拒绝，以及跨客户端访问和取消仍被拦截。

这些局部回归不能代替真实 Windows ACL、Docker、OAuth 和云端部署验收。已完成验证的时间、源码版本、运行副本与云端版本对应关系见[修复与验证快照](../../SECURITY-FIXES.md)；2026-10-31 的文档整理仅核对既有证据，不重跑上述业务检查。
